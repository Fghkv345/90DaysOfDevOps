 **##Part 1 — Linux File System Hierarchy **

Linux organizes almost everything under one directory tree beginning at /.

A useful mental model:

/
├── home/       → normal users' files
├── root/       → root user's home
├── etc/        → system configuration
├── var/
│   └── log/    → logs
├── tmp/        → temporary files
├── bin/        → essential commands
├── usr/
│   └── bin/    → most user commands
└── opt/        → optional/third-party software

1. / — Root Directory
Purpose

/ is the top of the Linux filesystem hierarchy. Every other directory ultimately exists somewhere below /.

Examples:

/home
/etc
/var
/usr
/tmp
Explore
ls -l /

You will typically see directories such as:

bin
boot
dev
etc
home
lib
opt
root
tmp
usr
var
I would use this when...

I need to understand the overall filesystem structure or locate a directory/file whose location I don't know.

2. /home — Normal Users' Home Directories
Purpose

/home contains the personal directories of normal users.

For example:

/home/shahab
/home/alice
/home/bob

Your personal files, documents, scripts, SSH configuration, etc. normally live under your home directory.

Explore
ls -l /home

You might see:

shahab

Then:

ls -la /home/shahab
I would use this when...

I need to find a normal user's personal files, scripts, SSH configuration, or application data.

3. /root — Root User's Home
Purpose

/root is the home directory of the root user.

It is different from /.

Important distinction:

/       → filesystem root
/root   → root user's home directory
Explore
ls -l /root

You may need:

sudo ls -la /root

because normal users generally cannot read everything inside it.

I would use this when...

I am troubleshooting something specifically belonging to the root user's environment.

4. /etc — Configuration Files
Purpose

/etc contains system-wide configuration files.

Examples:

/etc/hostname
/etc/hosts
/etc/passwd
/etc/ssh/
/etc/nginx/
/etc/systemd/

This is one of the most important directories for a DevOps engineer.

Explore
ls -l /etc

Try:

cat /etc/hostname

This displays the machine's hostname.

You can also inspect:

cat /etc/hosts
I would use this when...

A system or service behaves incorrectly and I need to inspect its configuration.

For example, if Nginx isn't behaving correctly:

/etc/nginx/

would be an important place to investigate.

5. /var/log — System Logs
Purpose

/var/log contains logs generated by the operating system and applications.

Examples can include:

/var/log/syslog
/var/log/auth.log
/var/log/kern.log

However, on modern systemd-based Linux systems, many service logs are stored in journald rather than ordinary files.

You can inspect them using:

journalctl
Explore
ls -l /var/log

Find large log directories/files:

du -sh /var/log/* 2>/dev/null | sort -h | tail -5
I would use this when...

Something went wrong and I need evidence of what happened.

For example:

Service failed
      ↓
Check status
      ↓
Check logs
      ↓
Find the actual error
      ↓
Fix the underlying problem

This is a fundamental DevOps troubleshooting pattern.

6. /tmp — Temporary Files
Purpose

/tmp is used for temporary files created by applications and users.

Examples:

/tmp/myfile
/tmp/application-cache

Files in /tmp should generally not be treated as permanent storage.

Explore
ls -la /tmp
I would use this when...

I need temporary storage while running a script, application, installation, or troubleshooting procedure.

For example:

echo "testing" > /tmp/test.txt
cat /tmp/test.txt
Additional Directories
7. /bin — Essential Command Binaries
Purpose

Historically, /bin contained essential executable commands required for basic system operation.

Examples include commands such as:

ls
cp
mv
rm
cat
Important modern Linux detail

On many modern distributions, including Ubuntu, /bin is a symbolic link to /usr/bin because of the /usr merge.

Check:

ls -ld /bin

You may see something similar to:

/bin -> usr/bin
I would use this when...

I need to understand where fundamental system commands are located.

8. /usr/bin — User Command Binaries
Purpose
/usr/bin contains a very large collection of executable programs available to users.

Examples:

python3
git
grep
ssh
vim
curl

Explore:

ls -l /usr/bin | head

You can find where a command comes from using:

which git

or preferably:

command -v git
I would use this when...

I need to locate or understand where an installed command/executable is coming from.

9. /opt — Optional / Third-Party Software
Purpose

/opt is conventionally used for optional or third-party software packages that don't fit naturally into the standard filesystem layout.

For example:

/opt/myapplication
/opt/vendor-software

Explore:

ls -l /opt
I would use this when...

I need to locate software that was installed as a self-contained third-party application.

The most important ones to really understand for DevOps are:

/etc
/var/log
/home
/tmp
/usr/bin

 **##Part 2 — Scenario-Based Troubleshooting **

The important concept is:

Don't randomly run commands. Gather information, interpret the result, then choose the next command.

A typical troubleshooting flow is:

Problem
   ↓
Observe
   ↓
Check status
   ↓
Check logs
   ↓
Identify error
   ↓
Investigate specific cause
   ↓
Fix
   ↓
Verify
Scenario 1 — Service Not Starting
Problem

myapp failed to start after a server reboot.

Step 1 — Check the service
systemctl status myapp
Why?

This is the first thing to check because it tells us the current state.

You might see:

Active: failed

or:

Active: active (running)

If it says failed, we now know we need to investigate why.

Step 2 — Check the service logs
journalctl -u myapp -n 50
Why?

The status tells us that it failed.

The logs may tell us why it failed.

For example:

Failed to bind port 8080

or:

Permission denied

or:

No such file or directory

These errors lead to completely different troubleshooting paths.

Step 3 — Check whether it is enabled
systemctl is-enabled myapp
Why?

If the problem appeared after reboot, we should determine whether the service is configured to start automatically.

Possible output:

enabled

or:

disabled
Step 4 — Check the complete recent journal
journalctl -u myapp --since "10 minutes ago"
Why?

This gives us more contextual information around the failure instead of only the last 50 lines.

Final troubleshooting sequence
systemctl status myapp
journalctl -u myapp -n 50
systemctl is-enabled myapp
journalctl -u myapp --since "10 minutes ago"
What I learned

Check status first, then logs, then investigate the specific cause shown by the logs.

Scenario 2 — High CPU Usage
Problem

The application server is slow.

We need to identify which process is consuming CPU.

Step 1 — Get a live view
top

Look at the %CPU column.

You may see something like:

PID     USER     %CPU    COMMAND
4210    app      98.5    python3
1520    root     12.3    nginx

The important information is:

PID = 4210
%CPU = 98.5

The PID identifies the process.

Exit:

q
Step 2 — Get a sorted process list
ps aux --sort=-%cpu | head -10
Why?

This gives you a snapshot of processes sorted from highest CPU usage to lowest.

The - means descending order.

So:

highest CPU
     ↓
lowest CPU
Step 3 — Investigate the specific PID

Suppose the problematic PID is:

4210

You can inspect it:

ps -p 4210 -f
Why?

We have moved from:

"The server is slow"

to:

"PID 4210 is consuming CPU"

Now we can determine exactly what process it is.

Step 4 — Monitor that process
top -p 4210
Why?

This lets us watch that particular process and determine whether the CPU usage is consistently high or only temporarily high.

Troubleshooting sequence
top
ps aux --sort=-%cpu | head -10
ps -p <PID> -f
top -p <PID>
What I learned

Start with system-wide observation, identify the problematic PID, then investigate that specific process.

Scenario 3 — Finding Docker Service Logs
Problem

A developer asks:

"Where are the logs for the Docker service?"

Docker is managed by systemd.

Step 1 — Check the service
systemctl status docker
Why?

Before investigating logs, confirm that the service exists and see its current state.

Step 2 — View recent logs
journalctl -u docker -n 50
Why?

-u docker means:

Show logs associated with the Docker systemd unit.

-n 50 means:

Show the most recent 50 lines.

Step 3 — Follow logs in real time
journalctl -u docker -f
Why?

-f means follow.

It behaves conceptually like:

tail -f

You can keep this running while reproducing a problem.

For example:

Terminal 1:
journalctl -u docker -f

Terminal 2:
docker restart <container>

Terminal 1 can then show what happens during the operation.

Press:

Ctrl+C

to stop following.

What I learned

systemd-managed services commonly use journald, and journalctl -u <service> lets me inspect that service's logs.

Scenario 4 — File Permission Problem
Problem
/home/user/backup.sh

produces:

Permission denied
Step 1 — Check permissions
ls -l /home/user/backup.sh

Suppose we get:

-rw-r--r-- 1 user user 500 Aug 11 10:00 backup.sh

Break this down:

- rw- r-- r--
  │   │   │
  │   │   └── others
  │   └────── group
  └────────── owner

There is no x.

Therefore the file isn't executable.

Step 2 — Add execute permission
chmod +x /home/user/backup.sh

This adds the execute bit.

Step 3 — Verify
ls -l /home/user/backup.sh

Now you should see something like:

-rwxr-xr-x

The important difference is:

-rw-r--r--
   ↓
-rwxr-xr-x

The x means execute permission is present.

Step 4 — Run it
./backup.sh

If it still fails, don't immediately assume permissions are the problem. At this point, investigate the new error.

For example, you could check:

head -1 /home/user/backup.sh

A shell script normally needs an appropriate shebang such as:

#!/bin/bash

You can also check the file type:

file /home/user/backup.sh
What I learned

First inspect the permissions, make the minimum required change, verify the change, and then test again.

The DevOps Troubleshooting Mindset

These four scenarios demonstrate four different troubleshooting categories:

Problem	First question	Main tool
Service failure	Is the service running?	systemctl
High CPU	Which process is responsible?	top / ps
Service logs	What happened?	journalctl
Permission denied	Does the file have execute permission?	ls -l / chmod

The deeper pattern is more important than memorizing commands:

                INCIDENT
                   │
                   ▼
             What is wrong?
                   │
                   ▼
             Gather evidence
                   │
        ┌──────────┼──────────┐
        ▼          ▼          ▼
      Status      Logs      Resources
        │          │          │
        └──────────┼──────────┘
                   ▼
             Identify cause
                   │
                   ▼
              Make a fix
                   │
                   ▼
                Verify
Commands worth remembering from Day 07
# Filesystem
ls -l /
ls -la ~
ls -l /etc
ls -l /var/log
ls -l /tmp

# Disk/log investigation
du -sh /var/log/* 2>/dev/null | sort -h | tail -5

# Configuration
cat /etc/hostname

# Services
systemctl status <service>
systemctl is-enabled <service>
systemctl list-units --type=service

# Logs
journalctl -u <service> -n 50
journalctl -u <service> -f

# CPU
top
ps aux --sort=-%cpu | head -10
ps -p <PID> -f

# Permissions
ls -l <file>
chmod +x <file>
One particularly important DevOps habit

Don't think:

"Which command should I run?"

Think:

"What information do I need next to narrow down the cause?"

That's the transition from learning Linux commands to actually troubleshooting Linux systems.
